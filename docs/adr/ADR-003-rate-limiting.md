# ADR-003: Усиление защиты Rate Limiting
Дата: 2025-10-15
Статус: Accepted

## Context
В P04 была реализована базовая защита rate limiting, но анализ показывает необходимость улучшений:
- Текущая реализация использует in-memory хранилище (не распределенное)
- Отсутствует дифференциация лимитов для разных типов пользователей
- Конфигурация жестко закодирована в коде
- Нет интеграции с системой мониторинга

Это создает риски:
- Возможность обхода ограничений в распределенной среде
- Неоптимальный UX для аутентифицированных пользователей
- Сложность операционного управления

## Decision
Усилить реализацию rate limiting со следующими улучшениями:

1. **Конфигурация через environment variables** для гибкости
2. **Дифференциация лимитов** по типам пользователей:
   - Анонимные пользователи: 10 запросов в минуту
   - Аутентифицированные пользователи: 100 запросов в минуту
   - Администраторы: 1000 запросов в минуту
3. **Redis-бэкенд** для распределенного хранения счетчиков
4. **Интеграция с мониторингом** - метрики для алертинга

Конкретные параметры (configurable):
```python
```
RATE_LIMITS = {
    "anonymous": os.getenv("RATE_LIMIT_ANON", "10/minute"),
    "user": os.getenv("RATE_LIMIT_USER", "100/minute"),
    "admin": os.getenv("RATE_LIMIT_ADMIN", "1000/minute")
}
```

## Alternatives
Рассмотренные альтернативы:

1. **Nginx rate limiting на уровне инфраструктуры**
   - Плюсы: высокая производительность, прозрачно для приложения
   - Минусы: инфраструктурная зависимость, сложнее кастомизация

2. **API Gateway с встроенным rate limiting**
   - Плюсы: богатый функционал, централизованное управление
   - Минусы: избыточно для текущего масштаба, дополнительные costs

3. **Оставить текущую in-memory реализацию**
   - Плюсы: простота, нет внешних зависимостей
   - Минусы: не масштабируется, сбрасывается при рестарте

Выбрано улучшение существующей реализации как оптимальный баланс.

## Consequences
**Положительные последствия:**
- Эффективная защита от brute force атак
- Гибкая настройка под разные роли пользователей
- Масштабируемость в распределенной среде
- Улучшенный monitoring и alerting

**Отрицательные последствия:**
- Усложнение конфигурации и развертывания
- Зависимость от Redis (дополнительный компонент инфраструктуры)
- Увеличение latency из-за сетевых запросов к Redis

**Компромиссы:**
- Баланс между безопасностью и производительностью
- Баланс между функциональностью и сложностью инфраструктуры

## Security Impact
- **Снижает риски:** R2 (DoS атаки) из P04 Threat Model
- **Соответствует NFR:** NFR-PERF-01 (защита от перегрузки), NFR-SEC-03 (контроль доступа)
- **Устраняет угрозы:** Denial of Service через флуд запросов

## Rollout Plan
**Definition of Done:**
- [ ] Реализована дифференциация лимитов по ролям
- [ ] Настроен Redis бэкенд для распределенного хранения
- [ ] Добавлены метрики для мониторинга
- [ ] Протестировано в staging окружении

**План внедрения:**
1. Фаза 1: Реализация конфигурируемых лимитов и Redis бэкенда
2. Фаза 2: Постепенное включение в production с мониторингом
3. Фаза 3: Настройка алертинга на основе метрик
